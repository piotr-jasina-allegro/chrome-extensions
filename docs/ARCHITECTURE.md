# Architecture

This repository contains the MV3 Chrome extension “Boring Stuff Helper”.
The codebase has been migrated to TypeScript and organized by runtime boundary:
background service worker, content scripts, popup side panel, and shared helpers.

## Layout

```text
src/
  background/
    index.ts        # MV3 service worker: install/context-menu/storage wiring
  content/
    content.ts      # content-script entry: detects the site and mounts per-site UI
    sites/
      adp.ts        # ADP (console.allegrogroup.com) helpers/buttons
      apreelts.ts   # apreelts.azurewebsites.net helpers/buttons
      jira.ts       # Jira / Google Sheets sprint issue fetch and storage
  popup/
    popup.html      # side panel shell
    popup.ts        # tab-aware side panel entry point
    jiraData.ts     # Jira summary renderer used by the side panel
  shared/
    types.ts        # shared TypeScript types
    utils.ts        # shared pure helpers (site matching, month math, Jira summary HTML)
```

`manifest.json` remains the source of truth for extension wiring, and Vite reads
that manifest through `@crxjs/vite-plugin`.

## Runtime responsibilities

### Background service worker

`src/background/index.ts` owns extension-level behavior:

- registers the side panel behavior,
- creates the context-menu toggle,
- initializes `chrome.storage.local.buttonsVisible`,
- flips `buttonsVisible` when the context menu is clicked.

### Content scripts

`src/content/content.ts` is the single content-script entry point. It:

- classifies the current page with `websiteMatches`,
- reads `buttonsVisible` from `chrome.storage.local`,
- re-renders when `buttonsVisible` changes,
- dispatches to the per-site setup functions in `src/content/sites/*`.

The site modules keep the page-specific logic isolated:

- `adp.ts` mounts the ADP buttons and reacts to DOM mutations,
- `jira.ts` fetches the active Jira sprint and stores monthly snapshots,
- `apreelts.ts` handles the AprEELTS helper flow.

### Popup / side panel

`src/popup/popup.ts` is the side-panel entry point. It watches the active tab,
matches the URL, and invokes the Jira renderer when the current page is Jira or
Google Sheets.

`src/popup/jiraData.ts` reads the monthly snapshots from `chrome.storage.local`
and renders them into the side panel. The popup cannot read a page’s
`localStorage`, so `chrome.storage.local` is the cross-context source of truth.

## Data flow

1. The background service worker initializes and owns the
   `buttonsVisible` toggle.
2. Content scripts load on supported pages and re-render whenever
   `buttonsVisible` changes.
3. The Jira content script fetches the active sprint issues from Jira, groups
   them by date, and stores the monthly snapshot as `issuesMont-YYYY-MM` in
   both `localStorage` and `chrome.storage.local`.
4. The popup reads the current and previous month snapshots from
   `chrome.storage.local` and renders the summaries in the side panel.

## Build and development workflow

The project uses Vite with `@crxjs/vite-plugin`.

- `npm run build` produces a Chrome-loadable `dist/` directory.
- `npm run dev` runs the Vite build in watch mode and continuously refreshes the
  generated output.

Because this is an unpacked extension workflow, Chrome still needs a manual
reload after rebuilds. Load the extension from `dist/`, not from the repository
root.

## Known preserved quirks

These behaviors are intentional and preserved for zero-behavior-change parity
with the original extension:

- `JiraIssue.parentKey` stays present in the type model even though real Jira
  responses do not populate it. The parent issue lives at
  `issue.fields.parent.key`, so the `parentKey` branch in the summary renderer
  remains effectively unreachable.
- `src/content/loader.ts` is intentionally not created. The MV3 content-script
  loader shim is generated by `@crxjs/vite-plugin`, so the manifest can point
  directly at `src/content/content.ts` in source.
